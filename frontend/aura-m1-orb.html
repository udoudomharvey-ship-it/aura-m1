    This component has no independent AI logic — it only visualizes a state fed to it externally.
    This page is dev-mode: the buttons above call orb.setState() directly, a
    simple 6-value demo API. Production (aura-m1-globe.html's HUD widget) never
    calls that — it goes through orb.setPerceptualState() instead, fed by
    hemm-perceptual-adapter.js's computePerceptualState(), which derives a
    multidimensional state (operational state, activity, Q_HCI trend, entropy, softmax-derived
    confidence/uncertainty, graded alert severity, and system health — kept as a genuinely separate
    color/visual channel from HCI alerts, so a software error never looks like a bad interaction) from
    real telemetry. Same renderer, same click/keyboard/reduced-motion handling, two different callers.
    


    Honest scope note: this remains a browser/Three.js renderer, not a native application shell
    — there's no way to build or verify Tauri/native integration in the sandboxed environment this was
    built in. The architecture (adapter → blended state → renderer, transport-agnostic input) is
    designed so an eventual native runtime could drive the same renderer without changes, but that
    integration itself doesn't exist yet. No voice command system exists anywhere in this project
    either, so voice hooks aren't implemented — there's nothing real to wire them to. True
    post-processing bloom was skipped in favor of additive blending, which is cheaper and lower-risk
    at this widget's size. See orb-core.js / orb-renderer.js / hemm-perceptual-adapter.js for the
    reusable implementation.
